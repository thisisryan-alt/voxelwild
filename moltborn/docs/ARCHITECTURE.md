# Architecture

Moltborn is plain ES modules loaded straight from `index.html`. There is no bundler, no transpiler and no asset
pipeline: every sprite, tile, cutscene, sound effect and song is generated by code when the game starts. This
document explains how the pieces fit together so that a change in one place does not surprise another.

## The frame

```
index.html
  src/main.js            creates the Engine and the Game, wires the page
    src/core/engine.js   canvas, integer-scaled presentation, fixed-step loop, scene stack
    src/game.js          Game: owns every system, builds worlds, saves and loads
```

* The canvas is 480x270 and is scaled by the largest integer that fits (or fractionally when the window is smaller than
  the canvas).
* The loop runs a fixed 60 Hz simulation step. `engine.step(dt)` updates only the top scene; `engine.render()` draws from
  the topmost *opaque* scene upward, so a translucent pause menu is drawn over the scene beneath it.
* `game.advance(n)` runs `n` simulation steps and one render. It is what the browser tests call, which makes the game
  deterministic under test: nothing in a test depends on wall-clock time. Anything delayed in game code therefore uses
  game time (see `Rifts.after`) rather than `setTimeout`.

### Scenes

A scene is any object with `update(dt)` and `draw(ctx)`, optionally `opaque`, `onEnter()` and `onExit()`. The stack is
`engine.scenes`; `push`, `pop` and `replace` manage it. `PlayScene` (`src/ui/playscene.js`) holds the world and the HUD.
Menus, shops, cutscenes, the fishing game, the help compendium and every other full-screen interaction are scenes pushed
on top of it, which is why the world pauses without any special-casing: only the top scene is stepped.

## The world

`World` (`src/world/world.js`) is built from a *zone*, a plain object produced by `ZoneBuilder`
(`src/world/zonebuilder.js`): a tile grid, spawns, props (interactables, pickups, signs), entries and exits, lights and
hazard areas. Zones are built lazily and always fresh; anything that must persist (opened chests, broken walls, killed
unique foes, forage cooldowns, fog of war) lives in `state.zones[zoneId]` and is re-applied when the zone is rebuilt.

### Zone DSL

Zone files in `src/data/zones_*.js` are written against the builder:

```js
const b = new ZoneBuilder({ id: 'reef_moonpool', name: 'Moonpool Cove', biome: 'reef', w: 92, h: 44, seed: 29, music: 'reef' });
b.fill(T.ROCK);                 // solid, then carve the open water out of it
b.carve(3, 6, 86, 34);
b.seabed(3, 89, (x) => 34 + Math.sin(x * 0.13));
b.platform(8, 31, 5);           // one-way platform, 5 tiles wide
b.exitW(26, 30, 'reef_garden', 'moon');   // an exit on the west wall; the entry name is on the other side
b.entryFloor('west', 5, { facing: 1 });
b.spawnFloor('pinchling', 22, 8, { count: 2 });
b.chest(8, { item: 'charm_moonpearl', coins: [40, 80] }, { secret: true, key: 'moonpool_cache' });
return b.finish();
```

`finish()` returns the zone object. After it, `buildZone` (`src/data/zones.js`) runs two placement passes that add
forage patches (`world/forage_place.js`) and fishing spots (`world/fish_place.js`) at deterministic spots derived from
the zone seed.

Exits may carry a `cond(game)` function; the world only changes zone if it returns true. Tidal Rifts use it to hold the
way shut until a chamber is cleared, and `Clock.gate()` uses it for passages that open only at night.

### Procedural zones

Two zone families are generated from their id alone, so the same id always builds the same cave:

| id | built by | used for |
|---|---|---|
| `rift:<seed>:<depth>:<max>` | `buildRift` in `world/rift_gen.js` | Tidal Rift chambers |
| `arena:<seed>` | `buildArena` | the Pearl Gauntlet |

Both are recognised by `isProcedural(id)`. They are never marked visited, never saved, never trigger story scenes, and
`Game.zoneState` hands them a temporary state map. A rift's last chamber has a single boss spawn (the Rift Warden) with
`repeat: true`, so it spawns even after it has been beaten once.

### Tiles, baking and lighting

`src/world/tiles.js` defines tile ids and solidity. `bake.js` pre-renders each biome's tile materials into a layer;
`tile_detail.js` adds per-tile detail (moss, cracks, glints) during the bake. `World.draw` renders, in order: background,
back layer of ambient events, tiles, entities, foreground, lighting (a darkness pass cut by light sprites), the glow
layer of ambient events, then `PostFX.apply` and finally flashes and the HUD, so interface text is never smeared by
post-processing.

## Entities

* `Entity` (`entities/entity.js`) has a position, a size and `moveBody` collision through `world/physics.js`.
  `Projectile` and `Pickup` live in the same file.
* `Player` (`entities/player.js`) is a small state machine (`free`, `walk`, `attack`, `dash`, `block`, `hurt`, ...). Its
  stats are recomputed by `computeStats(state)` in `systems/progression.js` from level, form, branches, skills, gear, sets,
  mutations and rift relics.
* `Enemy` (`entities/enemy.js`) is data-driven: a record in `data/enemies.js` names a behaviour in `entities/ai.js` (or
  `ai_rift.js`), a sprite plan and numbers. Behaviours are `{ init(e), update(e, dt, world) }` and communicate through
  `e.state` strings and `e.a`, their private scratch object.
* `Boss` (`entities/boss.js`) extends `Enemy` with an arena lock, phases, armour and stagger, telegraphs and a defeat
  sequence. A boss class lists attacks per phase and implements each attack as a generator method that `yield`s seconds.
  Bosses register themselves in `BOSS_CLASSES` and are created from a `spawn` record in the zone.
* Interactables (`entities/interactables.js`) are registered in `INTERACTABLES` by prop type: shrines, chests, signs,
  murals, NPCs, forage patches, fishing posts, the Tide Board, altars and relic stands.

### Status effects

`StatusSet` (`systems/status.js`) hangs off the player and every enemy. Combat code never asks "is the player chilled";
it asks `status.mult('speed')`. Definitions live in `STATUS`; a status with `passive: true` (Sunlit, Moonlit) has no
timer and comes from the tide clock rather than from a blow or a meal.

## Systems and the event bus

Systems are constructed in `Game`'s constructor and stored on `game.systems`. They talk through `game.events`
(`on`, `emit`), which is a plain synchronous bus. The events in use:

| event | arguments | emitted by |
|---|---|---|
| `zone` | zone id | `Game.buildWorld` |
| `kill`, `hitdealt`, `hurt`, `dash`, `stroke`, `parry`, `land`, `footstep` | combat details | enemies, player, body fx |
| `boss`, `bossengage` | boss key | boss lifecycle |
| `rift`, `arena`, `relic`, `altar` | `enter` / `depth` / `won` / `lost`, ... | rifts and the gauntlet |
| `wardenslain` | flawless? | the Rift Warden |
| `bounty`, `bountyboard` | bounty / streak | bounties |
| `fish` | species, length, `{ fresh, record, big }` | fishing |
| `sold` | item, count, coins | market |
| `phase` | phase id | the tide clock |
| `surge` | `warn` / `rush` / `calm` | tidal surges |
| `runlogged` | entry | run history |
| `crafted`, `ate`, `forage`, `order`, `chest`, `rest`, `travel` | | economy and exploration |
| `trophy`, `codex`, `cosmetic`, `levelup`, `evolved`, `questdone` | | progression |
| `setting` | key, value | options |

Notable systems: `Stats` (lifetime records), `Achievements` (99 trophies read from the records), `Story` (illustrated
cutscenes queued by events), `Quests`, `Dialogue` (generator-based scripts), `Codex`, `Crafting`, `Orders`, `Bounties`,
`Fishing`, `Market`, `Clock`, `Surge`, `Rifts`, `Arena`, `History`, `Difficulty`, `Elites`, `Barks`, `Director` (pack
tactics), `Access` (colour-blind and contrast helpers), `Captions`, `Cosmetics`, `Travel` and `Companion`.

## Saves and settings

* Saves are JSON in `localStorage` under `moltborn.save.<slot>` with a rolling backup at `moltborn.bak.<slot>`. If storage
  is unavailable the game keeps slots in memory. `Save.exportCode`/`importCode` turn a slot into a pasteable `MB1.` code
  with a checksum; `validate()` rejects damaged or inconsistent saves.
* `state` (see `newState()` in `systems/progression.js`) is the whole save. Newer systems create their part lazily
  (`state.bounties`, `state.fish`, `state.runLog`, `state.runBest`), so an older save loads without migration.
* Settings are stored apart from saves so they survive a deleted slot. They are described by one schema,
  `SCHEMA` in `systems/settings.js` (group, key, label, type, default, hint); the options screen, the defaults and the
  validation all read it, so adding a setting is one line.

## Rendering pipeline notes

* Sprites are painted procedurally by `gfx/painter.js` onto small canvases and cached by key. A *plan* is a function
  `(painter, t, options)`; `enemyFrame(key, sprite, pose, frame)` evaluates it once per pose and frame.
* `gfx/events.js` draws ambient sea life and weather in three layers (`back`, `front`, `glow`). New kinds are added to
  `KINDS` with `spawn`, `step` and `draw`; the surge, moonbeam and plankton events are examples.
* `gfx/post.js` applies colour grading per realm and per hour, bloom, refraction, heat haze, shock ripples and the
  low-health look, each gated by an option, with a frame-rate governor that drops the expensive ones when the machine is
  slow.

## Audio

`audio/audio.js` synthesises effects with WebAudio (`addRecipe` registers a recipe by name); `audio/compose.js` builds a
fixed 16-bar song per area from a motif; `audio/music.js` plays it with synthesised instruments and fades layers in
with combat danger; `audio/feel.js` mixes ducking, muffling and impact sweetening.

## Determinism and testing

Randomness in gameplay code uses `rng(seed)` from `core/util.js` where repeatability matters (zone generation, rift rooms,
daily boards, fishing rolls) and `Math.random()` where it does not (particles). See `docs/TESTING.md`.
